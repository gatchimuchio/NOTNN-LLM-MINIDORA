# MINIDORA 公開境界・漏洩危険性監査 2026-09-20

## 0. 監査目的

公開リポジトリから、非公開の内部理論・抽象定義・固定概念を第三者が直接取得、または複数資料を組み合わせて再構成できる危険性だけを監査する。

本書は内部理論の内容を説明しない。具体的な定義、式、導出規則、完全な概念分解も再掲しない。

監査対象基点:

- repository: `gatchimuchio/NOTNN-LLM-MINIDORA`
- commit: `8862a9b5178df692ce8f204df3a2a193c53772f9`
- default branch上の公開ソース、設計文書、評価文書、構文化成果、ツール
- 公開Release metadata
- 公開commit metadata

## 1. 判定基準

公開コードそのものは直ちに漏洩とは判定しない。

危険と判定するのは、次のいずれかを満たす場合である。

1. 非公開の抽象定義を直接記載する。
2. 抽象定義をほぼ一意に再構成できる責任分解・不変条件・関係を一か所へ集約する。
3. 内部理論と実装箇所を対応付ける索引を公開する。
4. 同じ変換の大量の入力・出力対応を公開し、内部規則を推定可能にする。
5. 複数版の設計差分を公開し、変更差から内部規則を逆算可能にする。
6. 削除済みであっても、公開履歴・Release・配布物から取得可能である。

リスク区分:

- **CRITICAL**: 大量再構成・ほぼ完全な規則推定へ直結し得る。
- **HIGH**: 複数資料を組み合わせれば内部抽象へ近づける。
- **MEDIUM**: 単独では限定的だが、他資料と結合すると推定を助ける。
- **LOW**: 実装事実・性能事実に留まり、抽象定義への寄与が小さい。

## 2. 結論

### 2.1 直接漏洩

**今回の監査範囲では、取り扱い注意の学習関連抽象定義そのものを固定した直接記載は検出しなかった。**

default branchの関連語検索では、一般法則化を否定する記載や実装上の経験記録は確認したが、非公開の完全定義そのものとは判定しない。

commit messageの関連検索でも、学習関連の完全定義を示す見出しは検出しなかった。

したがって現時点の判定は:

```text
直接的な完全定義の漏洩: 未検出
間接的な再構成危険性: HIGH
```

「未検出」は完全不存在の証明ではない。GitHub検索で取得できない削除済みobject、外部mirror、過去に取得された配布物までは保証しない。

## 3. 検出事項

### A. 上位参照先への直接導線

**危険度: HIGH**

公開default branchで、内部理論の上位参照先へ直接到達できる記載を **12ファイル** で確認した。

そのうち **6ファイル** は、単なる参考資料ではなく、実装に対する上位の権威・正本に相当する位置付けまで公開している。

主な露出面:

- `README.md`
- `README.en.md`
- `AGENTS.md`
- `参照正本.md`
- `src/README.md`
- `設計/README.md`
- その他の設計・構文化文書

危険性:

- 第三者に「どこを読めば理論側へ到達できるか」を教える。
- 理論資料と実装資料の照合を容易にする。
- 単独では不明なコード上の意味を、上位資料から補完できる。

### B. 責任分解の集約

**危険度: HIGH**

中央の実装規約と複数の設計文書に、実行主体、状態管理、作用選択、再実行、採否、検証などの責任関係が比較的まとまった形で存在する。

個々の記述は実装説明として成立しているが、複数文書を横断すると、

```text
内部抽象
→ 実装上の責任
→ 型
→ 実行経路
```

の対応が追いやすい。

これはコード単体の公開より危険度が高い。コードを読む前に抽象構造の索引が与えられるためである。

### C. 理論と実装の対応索引

**危険度: HIGH**

公開文書の一部は、上位概念・構文化・実行核・能力部品・評価までを同一ページまたは相互リンクで結んでいる。

危険性は内容単体ではなく、**対応表としての機能**にある。

第三者は実装をゼロから読む必要がなく、公開文書のリンク構造そのものを探索順序として利用できる。

### D. 大規模な変換成果物

**危険度: CRITICAL**

公開Release metadata上で、大規模な変換済み成果物のZIP配布を確認した。

確認できた公開配布は少なくとも2世代あり、説明上は以下の規模を持つ。

- 96 shard
- 497,220単位の変換済み成果
- 約95MB級のZIP
- 元の公開revisionが固定されている

内部抽象定義が文章として書かれていなくても、

```text
固定された公開入力
+
大量の変換出力
```

が揃うと、変換規則・分類軸・意味座標を統計的・差分的に推定するための教師データとして利用され得る。

本監査ではこの面を**最大の漏洩危険**と判定する。

成果物の中身を全件再解析した判定ではないため、「実際に完全理論が復元可能」と断定はしない。しかし、公開継続の必要性は最優先で再評価すべきである。

### E. 複数版の設計履歴

**危険度: HIGH**

現行版だけでなく、旧設計・構文化履歴・比較文書が多数保持されている。

単一版では曖昧な実装判断でも、

```text
旧版
→ 変更理由
→ 新版
```

を比較すると、不変部分と修正部分を分離できる。

これは内部原理の候補を絞る強い情報になる。

履歴保存は再現性には有効だが、秘匿対象を持つ公開リポジトリでは、再現性と情報保護が衝突する。

### F. commit / Release履歴

**危険度: HIGH**

公開commit metadataには、抽象概念や内部原理を示唆する過去の見出しが残る。

またReleaseはdefault branchから独立して公開資産を保持する。

したがって、将来default branchだけを整理しても、

- commit history
- tags
- releases
- release assets
- fork / mirror
- 既取得物

には残存し得る。

### G. 実装識別子・コメント

**危険度: MEDIUM**

ソースには内部由来の識別子や説明コメントが広く残る。

ただし本監査では、**コードが具体的な一射影として存在するだけなら、それ自体を直ちに漏洩とは判定しない。**

危険度が上がるのは、次の組合せである。

```text
コード
+
完全な抽象説明
+
上位参照先
+
大量の変換例
```

この組合せが第三者の再構成コストを大きく下げる。

### H. ベンチマーク・性能値

**危険度: LOW**

正答数、速度、作用回数、回帰結果などの外部性能値は、それだけでは内部抽象定義を復元する情報量が小さい。

ただし、特定の理論変更と特定の性能差を細かく一対一対応させた公開履歴は、差分推定に利用され得るためMEDIUMへ上がる。

## 4. 漏洩経路の優先順位

| 優先 | 経路 | 危険度 | 理由 |
|---|---|---|---|
| P0 | 大規模な変換済み配布物 | CRITICAL | 大量の入出力対応が規則推定へ使える |
| P0 | 上位参照先への直接導線 | HIGH | 理論と実装の照合コストを下げる |
| P0 | 抽象責任と実装責任の対応表 | HIGH | コードの意味を先に与える |
| P1 | 複数版の設計・構文化履歴 | HIGH | 差分から不変条件を推定できる |
| P1 | commit / Release履歴 | HIGH | default branch整理後も残る |
| P2 | 実装識別子・コメント | MEDIUM | 単独では限定的だが結合時に効く |
| P3 | 性能値 | LOW | 抽象復元への寄与が小さい |

## 5. 推奨是正

本PRでは監査だけを行い、以下の是正は実施しない。

### P0

1. 公開リポジトリから上位内部理論への直接リンクと「上位正本」としての説明を外す。
2. 大規模な変換成果物の公開継続を再判定する。秘匿対象の意味射影を含む場合は、公開Release資産から外し、内部保管へ移す。
3. 公開設計書はインターフェース契約・入出力・受入試験へ限定し、内部抽象と実装の完全対応表を置かない。

### P1

4. 旧設計・構文化履歴を、公開再現性に必要なものと内部監査用のものへ分離する。
5. 公開コードのコメントは「何を保証するか」までに留め、「なぜその内部原理になるか」を説明しない。
6. 新しい適応・学習機能は、公開時に実装挙動と試験結果だけを示し、抽象定義を説明しない。

### P2

7. default branchだけでなく、commit history / tags / releases / release assetsを別途監査する。
8. 公開前監査をRelease作成前にも必須化し、生成ZIPや自動成果物を対象に含める。

## 6. 公開可能性の基準

今後、公開してよい情報の目安を次とする。

### 公開可

- 実装コード
- API・入出力契約
- 局所アルゴリズム
- テスト
- ベンチマーク結果
- 制限事項
- 失敗時の挙動
- モジュールの交換可能性

ただし、これらを組み合わせて完全な抽象定義が再構成できる場合は再判定する。

### 非公開維持

- 完全な抽象定義
- 固定された原理式
- 理論全体の最小分解
- 理論から実装への完全対応表
- 抽象概念を一意に復元できる大量の教師データ
- 未公開定義の変更履歴と差分理由

## 7. 監査限界

本監査は、GitHub上で取得できた現行default branch、公開Release metadata、commit metadataを対象とした。

次は未完了である。

- 全Git objectの履歴走査
- 削除済みbranchの到達不能object
- fork / mirror
- 検索エンジンcache
- 第三者が過去に取得したZIP
- 公開Release ZIP内部の全件意味再解析

したがって、**「直接定義を未検出」=「過去を含めて漏洩が絶対にない」ではない。**

## 8. 最終判定

```text
直接の完全定義漏洩     : 未検出
実装コード単体         : 許容可能
文書による抽象構造露出 : HIGH
理論と実装の対応導線   : HIGH
大規模変換成果物       : CRITICAL
履歴からの再構成       : HIGH
総合                    : HIGH
```

現状の主問題は、秘密そのものを一文で公開していることではない。

**公開資料を横断したとき、第三者が内部抽象へ到達するための探索コストが低すぎること**である。

今後の公開境界は、「コードを隠す」ではなく、**完全な抽象、完全な対応関係、大量の変換教師データを同時に公開しない**ことを中心に置くべきである。
