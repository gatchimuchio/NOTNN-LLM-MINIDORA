## 変更前後の具体例

詳細入力・本文・状態・経路は [開発診断JSON](第25バッチ_開発診断.json)。両版へ同じ依頼を公開の `製品ミニドラ()` から渡した。

| 開発課題 | 変更後 |
|---|---|
| 資料に基づいて命題を「判断して」 | 通常命題経路で支持を導出 |
| 「判定してくれる？」 | 追加能力へ自動接続して支持を導出 |
| 「判断して、短く説明して」 | 命題と短縮指定を保持して回答 |
| 「もう少し短く説明して」 | 原成果を変更せず再説明 |
| 明示されたネコ・猫の述語同値＋所属＋全称規則 | 定義を根拠として哺乳類への所属を導出 |
| 提供規則からの仮説候補構成 | AとBを競合仮説として保持し、由来を提示 |
| Bへの介入 | 上流Aを書き換えず、明示モデル内で比較 |

変更前の一部は、処理不能の本文を短く変換する作用だけが「合格」になる。これを元の問題を解いた正答として数えない。7能力課題と1境界確認は開発診断であり、汎用チャット正答率には換算しない。

## 仮説の規模改善

16候補から最大6個の対象組合せ14,893組という入力で、変更前は試行上限により停止した。変更後は観測への関連外14,891組の閉包評価を省略し、候補集合の評価2回でAを包含極小説明として返す。別途、背景整合性の検査1回を行う。

列挙・関連前提の逆参照・導出根拠の抽出・追加確認候補の構成にも操作予算をかける。全ての16候補問題が通る保証ではなく、候補数・仮説数・実評価・操作の上限は残る。途中結果を採用しない検査も維持する。

## 環境障害の区別

最初の基点試験は5 FAIL／3 ERRORだった。同じ変更前コードで調査した結果、このサンドボックスの通常ディスク領域では `os.fsync` が `OSError: [Errno 5] Input/output error` を返した。`/dev/shm` はfsyncを実行できたため、一時領域をそこに指定して基点と変更後を再測定した。製品コードのfsyncを削除・無効化・例外握り潰しにしていない。

通常領域へのeditable installも同じEIOで未完了。wheelを構築し、fsync可能な別仮想環境へ通常インストールする方法では導入・実CLIまで通った。入れ子venvでは最初にbuild backendのsetuptools未検出も起きたため、構築済みwheelの導入と分離した。これらを製品機能の失敗やWindows CIの結果へ読み替えない。

## 再実行

パッケージ導入後、リポジトリ根で実行する。

```text
python tools/repository_consistency_check.py
python tools/日本語基底監査.py
python -m compileall -q src tests tools
python -m unittest discover -s tests -v
python tools/規模測定.py
python -m minidora "2+3"
minidora "2+3"
python tools/第25性能確認.py
```

Linuxサンドボックスの一時領域がfsyncを提供しない場合だけ、対応領域へTMPDIRを設定する。通常Windows／Linuxでfsyncを無効化する設定は必要ない。
