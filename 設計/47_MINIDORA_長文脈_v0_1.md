# MINIDORA 長文脈管理 v0.1

日付: 2026-09-11
基点commit: `ae3c828418795bd5e41b78a7801b2697ee6c6aa1`
対象: 開発一覧⑪。原記録を保持した作業文脈の選択・再参照・明示改訂。

## 1. 作用と責任

```text
原記録（資料・成果・条件・残差）と明示された依存
→ 所有者・世代・改訂付きの起点
→ 必須記録・固定記録・条件・残差と依存先を選択
→ 予算内で語一致・直近の任意候補を追加
→ 原文と構造化Dataを保持した作業文脈
→ 既存能力・既存会話セッションへの素材
→ 採用済み成果を使用文脈への依存付きで明示登録
```

原記録の保持と、今回使う作業文脈を分ける。作業範囲から外れた記録は削除・要約で上書きしない。後の依頼で再選択できる。

状態があるだけではなく、直近範囲外の原文を選択して実際の数値抽出へ渡すこと、原資料の改訂が旧成果の利用可否と後続出力を変えることを接続試験で確認する。

Coreの記憶やHDSの採否を置換しない。世界知識や問題別正解を初期資産へ追加せず、呼出側が登録したDataだけを使う。GPQA正本のLIVE_ONLY境界への保存参照再投入機能ではない。

| `src/minidora/長文脈接続.py` | 起点と選択要求をDataとして渡す既存Capability Adapter。 |

既存の第3バッチの会話参照記憶・文脈付き要求セッションには変更を加えない。既存セッションに「本文」として選択素材を渡し、そこでの実HDS処理と次turn照応へ接続できる。短期セッションの64応答上限を解除したわけではない。原記録を登録するAPIと短期セッションの寿命管理は別責任。

## 3. 原記録と明示改訂

`文脈登録`は識別子、既存`能力結果`の内容、種別、依存ID列、固定指定を持つ。本文・根拠・参照資料・JSON互換Dataを既存の結果契約で保持する。

同じ記録IDを再利用して上書きしない。改訂は、旧IDの明示失効と新IDの追加を一つの更新で行う。理由は必須。旧記録は`原記録`で、現行可否・失効理由付きの履歴として確認できる。

依存先は同じ更新内も含めて先行する現行記録のみ。欠落先、自己参照、前方参照を拒否し、有向非循環構造を保つ。失効した原記録に依存する成果も推移的に現行利用から外す。本文は削除しない。

固定された記録や条件・残差が、依存元の失効によって利用不能になった場合は、それを黙って除外して成功しない。該当記録の明示失効・再登録による整理まで選択を保留する。必要な改訂対象を呼出側が選ぶ必要があり、自然言語による訂正の解釈や条件の自動継承ではない。

後付けの留保や関連資料を意味から発見して依存を補完する機能はない。依存関係と種別を適切に宣言する責任は上位にある。

## 4. 選択と依存閉包

`文脈選択要求`は必須ID、検索語、直近件数、作業予算を持つ。

必須ID、固定指定、種別が条件・残差の現行記録を最初に選び、それらが依存する全記録を推移的に含める。このまとまりが予算を超える場合は、依存や原文の一部を切らず保留する。

残りの予算では、指定語のNFKC/casefold部分一致数が多い順、同点では登録が新しい順に候補を試す。語一致がなくても指定した直近件数の記録は候補となる。各候補も依存先込みで入る場合だけ追加する。出力順は順位ではなく原記録の登録順である。

語一致は取得順序のヒューリスティックであり、同義語・含意・話題理解・真偽・必要情報の十分性を判定しない。明示必須IDは一件でも不在・失効なら保留。検索語の存在自体を必須条件とはせず、選択成功から「問いに必要な知識が揃った」とは判断しない。

原記録の全体と選択範囲を混同しない。選択結果には選択ID、省略ID、無効IDと選択理由を残す。作業包にも現行総数・選択数・省略数・無効数・全現行収録の真偽を含める。長い省略ID一覧は作業包の外に置き、記録としては保持する。

## 5. 予算の対象

予算は`文脈選択.包`の**UTF-8 JSONバイト数**である。本文だけでなく、選択された記録の構造化Data・参照資料・役割・依存・起点・収録範囲を含む。トークン数の推定や、LLMの実コンテキスト長とは呼ばない。

`資料化`は、選択した全記録の本文を二つの改行で連結し、原文の対応位置と完全な選択包をDataに保持する。各本文自体を削除・要約・正規化しない。参照資料は既存契約で結合し、同一IDの内容衝突は拒否する。

**資料化後の`能力結果`全体、合成器のログ、下流のプロンプトには別のサイズがある。** 選択包の予算が、それら全体のサイズやトークン数を保証するわけではない。包と本文を重複格納する診断形式も含むため、実運用の入力窓制限は下流で別途計数する必要がある。

一つの巨大文書を意味的に分割する機能はない。記録は不可分で、予算内に入らない必須記録は保留する。記録分割の単位、条件・留保の同伴、原文参照は上位で明示する。

## 6. 役割と採否

資料・成果・条件・残差の種別はDataとして保持し、記録の本文に書かれた命令を新しい実行権限にしない。条件・残差が作業窓にあることと、下流Moduleがその意味を理解して遵守することは別である。本Moduleは意味的制約の強制器ではない。

選択成立は選択契約の充足であり、全記録の事実性や資料処理の成立ではない。不成立の`能力結果`も原記録には保持できるが、成果種別としては受理しない。選択内に不成立記録がある場合、資料化は保留し、実行可能な本文へ昇格させない。

`成果登録`では現行選択・資料化契約・成果の成立を確認し、使用した全選択IDを依存へ記録する。結果が本当にその資料から導かれたかという意味的検証は、結果を作るModuleと上位の採否が担当する。

## 7. 状態版と保存・復元

所有ID、世代、改訂、追記履歴のハッシュを起点にする。同じ表示用セッションIDでも別インスタンスは別所有者。選択と、その後の資料化・成果確定では現行起点を照合する。原文や省略情報の改変は同じ選択要求から再選択して検出する。

更新はロック内で候補状態を作り、参照・サイズ等の全検査に成功した場合だけ反映する。競合更新は同じ起点から一方だけが確定する。公開する原記録や結果は複製し、呼出側の可変値変更を原本へ反映しない。

保存・復元はJSON文字列のAPIを提供する。ファイルI/O、暗号化、OSの永続化、保存先管理、利用者認証は追加しない。復元時は全イベントを再適用し、契約・順番・ハッシュ連結を確認する。重複JSONキー、未知項目、非有限値を拒否する。復元後の所有IDは新しく、以前の選択オブジェクトは利用できない。

ハッシュは内部整合の検査であり、署名・認証・原資料の真正性を保証しない。元資料と全履歴のハッシュを共に作り直す操作への保護ではない。

明示的な`初期化`は原記録を破棄して世代を進めるAPI。通常の選択や予算超過では破棄しない。必要な保存は初期化前に上位が行う。

資料化して返した値を、後で他の処理へ持ち出した後まで失効制御が自動追従するわけではない。実利用時の照合と成果確定は本庫の境界で行う。既存短期セッションに既に残った成果を同時に書き換える処理は追加しない。

## 8. 上限と非保証

既定4096記録、原記録保存16,000,000バイト。構築時の上限は最大16384記録・64,000,000バイト。更新履歴は16384件、単一記録は1,000,000バイト。失効記録も保存数・容量を消費する。上限超過で古い根拠を剪定しない。

選択包は既定32768バイト、最大1,000,000バイト。必須IDは128件、検索語16件、直近候補128件まで。正確なバイト数を計算するためシリアライズを行い、復元は履歴を順に再適用する。この版は大規模な索引最適化・厳密なCPU/メモリ隔離を提供しない。

合成器経由の停止は既存の呼出前後の停止検査に従う。選択処理途中のコールバック中断、非同期実行、外部検索は追加していない。

## 9. 実行と検証

```bash
python tools/長文脈デモ.py
python tools/長文脈デモ.py --値 731
python -m unittest discover -s tests -p 'test_長文脈*.py' -v
```

局所デモは101記録中の古い原資料1件を4096バイト予算で選び、既存抽出に渡す。保存・復元後の抽出結果は同じ。新しい原資料を731として追加し旧版を明示失効すると、旧選択は使えず、新しい値を抽出する。未保存の庫では後段の抽出を呼ばない。

実HDS接続試験では、既存の文脈付き要求セッションに選択素材を渡して文書操作を実行し、次turnの「それ」による参照を通す。これは自由な長会話全般の理解や、標準チャットへの自動接続の完成ではない。
