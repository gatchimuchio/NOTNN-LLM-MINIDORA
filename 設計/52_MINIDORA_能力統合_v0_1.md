# MINIDORA 能力統合・調整 v0.1

日付: 2026-09-11
基点commit: `baa007ea35d393d625f1ef351fd1392a12d6dac3`
対象: 第1〜第15バッチの共通実行・検証・採用・会話接続。第16バッチ。

## 1. 目的と実装範囲

個別に呼び出していた能力を、同じセッションの入力・計画・実行・結果検証・採用へ接続する。GUIの追加、Coreの置換、既存ベンチマークの更新ではない。

```text
日英文書依頼 → 既存の実HDS・要求解釈 ─┐
単一能力と明示Data ─────────────────┼→ 共通の能力合成器
構造化された複合計画と受入条件 ─────┘       ↓
                                 29能力から必要な工程を実行
                                           ↓
                                  全出力と最終条件の検査
                                           ↓
                              成功成果だけを会話・原記録へ採用
                                           ↓
                               次の依頼で照応・再参照・再利用
```

自由文入口が自動で計画化できる範囲は、既存の日英文書操作の限定文法である。それ以外の数学、コード、関係、ブラウザ等は、明示した能力入力や計画で同じ実行器へ入る。29能力の登録を、任意の自由文を29能力へ自動分解できることと同一視しない。

## 3. 計画と最終受入

`統合セッション.準備`は既存の`合成計画`と名前付き`能力結果`Dataを受ける。元の最終出力に対して`受入条件`を追加できる。条件は対象出力、検査能力、設定参照、基準資料の参照列を持つ。Dataの値を計画の命令文字列へ埋め込まない。

受入検査は同じ依存グラフの最終工程として実行する。成果検査、コード検証、数学結果採用、関係判定採用、記載値採用、文書の型検査だけを認め、外部読取や単なる素材引継ぎを検証器として扱わない。全件が成立するまで元の最終出力も採用しない。検証用の結果自体は利用者向け出力から除く。

条件が指定されない構造化計画は既存能力・合成契約の成立までを採用条件とする。例えば自由解の診断報告も成立し得る。一意解を要求する場合は明示した数学結果採用を付ける必要がある。受入条件の意味的な妥当性を統合器が自動発見するものではない。

準備した計画はセッションの所有ID・世代・改訂、全Data、能力名・版・外部読取区分と共にhashへ結び付ける。実行前に再照合し、旧計画・別所有者・改変・版変更を拒否する。同一セッションの同時処理は拒否する。ロック取得直後に起点を読み直し、取得前の状態を用いて外部作用へ進まない。

## 4. 採用状態と権限

成功成果だけを会話焦点と原記録へ登録する。計算が途中まで成功しても、最終検証・回答サイズ・履歴容量・停止確認等が不成立なら最終本文と出力を返さず、会話の最後の成功成果を上書きしない。診断用の途中実行記録は成功と区別して返す。

長文脈庫への原子的更新が成功してから、統合会話履歴を更新する。出力には提供された全Dataへの保守的な依存を付ける。意味的に必要な資料だけの依存抽出ではなく、同じ資料の重複保存も現時点では許す。原記録の保存文字列と照会APIはあるが、統合セッション全体の永続化・復元・自動改訂伝播を完成したものではない。

日英の次依頼は、横断する採用成果から既存の会話参照記憶を再構築して実HDSへ渡す。構造化数学の出力も、次ターンの「それ」の対象にできる。複数出力で曖昧な場合は勝手に一つを選ばず、出力番号等の明示が必要である。HDSIR自体の長期履歴を新規に保存する機構ではない。

外部読取はセッション構築時の許可と各構造化実行時の許可を両方必要とする。JSON本文や資料中の命令から許可を推定しない。知識取得・ブラウザ取得の失敗を固定参照で埋めない。最終採用が失敗しても、既に行われたGETを取り消せるわけではない。送信・購入・任意ファイル実行等は新規に追加しない。

## 5. 調整内容

### 純粋な部品結果の再利用

明示した25部品だけを対象とする、セッション内の有界LRUを追加した。キーは能力名・版と全能力文脈を含み、本文・設定・参照・セッション等のどれかが変われば別入力になる。失敗は保存せず、外部取得・可変原記録選択・探索全体も再利用しない。返却と保存は複製して可変値の汚染を避ける。

各能力の判定と合成器の整合検査は毎回実施する。hit時は本体の純粋な処理・内部再構成を再実行しない。これは同じ実装・入力・版に対する過去成功結果の再利用であり、独立した再検証ではない。依存コードの変更は版更新を要する。強いメモリ改ざん耐性や認証ではない。

既定64件・JSON換算4 MB、最大設定256件・16 MB。OSメモリ量を制限する仕組みではない。初期化で消去し、別セッションとは共有しない。GPQA正本への固定参照再投入や性能値更新とは無関係である。

### 全項目の箇条書き変換

旧変換本体の12項目切断を、統合経路の箇条書きに限って全項目保持へ変更した。20項目の対照では旧12項目に対し統合20項目。元の標準入口と旧Moduleは変更していない。上限超過は切断せず保留。句読点・改行の規定分割であり、意味的な文章構造解析の完成ではない。

## 6. 通信と利用例

```bash
python tools/統合チャット.py --一覧
python tools/統合チャット.py
python tools/統合検証デモ.py --反復 5
```

標準入力へ1行1JSONで渡す。各行は同じセッションで順番に処理する。

```json
{"種別":"能力","能力":"記号演算","入力":{"データ":{"式":"(x+1)**3","変数":["x"]}},"設定":{"操作":"微分","対象変数":"x"}}
{"種別":"依頼","依頼":"それから数字を抽出して"}
```

資料付きの文書依頼は次の形。

```json
{"種別":"依頼","依頼":"本文から数字を抽出して","資料":{"本文":"売上は731です。費用は75です。"}}
```

単一能力の操作だけでなく、`種別=計画`では既存合成計画、Data、最終受入条件を渡せる。具体的な複合例は`tests/test_統合実行.py`および既存デモの計画を参照する。上の能力結果や診断を一般的な会話回答へ言い換える機構は追加しない。

JSONの重複キー・非有限値・未知項目を拒否する。要求は2 MB以内。長すぎる入力行は後半を独立した依頼にせず終了する。JSONL CLIはHTTPサーバ・認証・GUI・インストーラではなく、既存標準チャット入口も変更しない。

## 7. 上限と未完成範囲

統合履歴は既定64応答・設定最大256応答、回答は最大100000文字、採用履歴2 MB、最終検査32件。既存合成器の工程数・Data上限、長文脈庫の件数・容量も適用される。履歴再構築は履歴長に伴う費用があり、上限解除や索引最適化ではない。

各部品の同期呼出中の強制終了、OS隔離、壁時計総時間保証、下流の任意コードからの完全な隔離は未実装。停止は既存の検査境界に従う。

これは15領域を同じ実行・採用系へ通した統合初版。自由な依頼全般からの目的・解法・能力組合せの発見、知識の意味的十分性、一般言語生成、標準チャット自動配線、GPT-4同条件比較は未完了である。29部品の登録数やテスト件数を総合知能の到達証拠にしない。
