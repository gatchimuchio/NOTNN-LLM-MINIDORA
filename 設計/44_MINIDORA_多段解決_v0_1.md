# MINIDORA 目的分解・多段解決 v0.1

日付: 2026-09-10
基点commit: `ec6a45cfba9827f56d8ec7614606935bcdac7c5c`
対象: 開発一覧⑧の、宣言された有限解法に対する目的駆動の分解・検証・後戻り。

## 1. 追加する作用

```text
最終目的 + 目的ごとの検証契約 + 利用可能な解法群 + 初期Data
→ 目的に対応する解法を選択
→ 必要な下位目的へ分解
→ 子の成果を入力に既存能力を実行
→ 目的に属する検証能力で候補を検査
→ 親・後続も成功すれば採用
→ 失敗なら下位目的の別解や親の別解へ戻る
```

第1バッチの明示計画実行を置き換えず、各処理・検証の呼出には既存合成器を使う。今回の違いは、全工程が決まった計画を入力するのではなく、目的と解法候補から実行経路を選び直すこと。解法が「成功する」と宣言しただけで目的を達成済みにしない。

有限のAND/OR分解を用いる。下位目的は全件必要、解法は候補のいずれかを使う。最初の子の成功で探索を打ち切らず、親や後続が失敗した場合は子の別候補まで戻る。複数最終目的も同じ後戻りの対象とし、すべて検証を通った一つの枝だけを返す。

## 2. 入出力と責任

| 型 | 責任 |
|---|---|
| `解決目的` | 目的ID、検証能力、検証指示・設定・追加資料のData参照。検証器は解法ごとには変えない。 |
| `解法` | 達成対象の目的、下位目的、処理能力、入力参照、指示・設定参照、探索優先度。 |
| `問題素材` | 初期Dataか、明示した下位目的の成果かを区別。 |
| `多段問題` | 最終目的、目的群、解法群。Data実値は含めない。 |
| `多段結果` | 全最終出力、採用枝の中間成果と経路、失敗を含む探索履歴、終了理由・予算・ハッシュ。 |

対象資料・数値・検証設定は初期Dataへ分離する。資料中の文章から新しい能力名や命令を実行しない。目的名を初期Dataに書いても、目的達成の証拠として使わない。

直接の入力は構造化された目的・解法であり、任意の自然言語からの意味解釈ではない。何を目的とし、何を有効な解法・検証基準とするかは上位の宣言責任。HDSをこの探索アルゴリズムへ置き換えない。

## 3. 探索・採用と状態

各目的では、優先度の小さい順、同順位では解法ID順に探索する。これは明示された実行順序であり、正しさや事実を多数決・文字順で選ぶものではない。最初に全目的を満たした経路を返し、最適性は主張しない。

成功した下位目的の成果は同じ枝の中で再利用できる。成果・検証条件・初期Dataは枝内で変更しない。親の条件未達時は再利用済みの成果にも戻り、別の組合せを調べる。失敗した枝の中間成果を新しい枝の入力や最終出力へ混入させない。

同じ目的へ再帰して戻る循環経路は切るが、別の非循環解法は探索する。解法が宣言されていない目的は未完了。未登録能力・不正な入力参照等は実行前に拒否し、未指定のCoreや外部LLMへ委譲しない。

`局所成立`は子や候補がその時点の検証を通ったという履歴であり、最終採用ではない。採用経路を別フィールドに残す。全目的不成立、予算超過、中止では最終出力・採用中間結果・採用経路を空にする。診断履歴は残す。

## 4. 処理と検証の接続

`多段解決器`は、処理能力と検証能力をそれぞれ既存の能力合成器で呼ぶ。指示、設定、素材の参照を呼出ごとに局所化し、全会話や他の枝の結果を暗黙に渡さない。目的検証は候補成果と、目的が明示した初期検証資料を入力に取る。

補助Moduleは次の二つ。

- `素材引継ぎModule`: 単一素材を型・内容・参照を保って引き継ぐ。
- `成果検査Module`: 非空、または元資料の数値列保持を検査する。

数値列保持は既存の数値抽出器で候補・原資料の数値列を取り、順序・重複を含めて照合する。意味全体の同値性、数値が対応する対象の正しさ、事実性を認定する検証ではない。既存抽出器の文法と限界を継承する。

第7バッチの`関係制約Module`を処理、`関係判定採用Module`を目的検証として使用できる。関係の未確定や前提矛盾を、検証を緩めることで成功にしない。既存証拠の適用条件・時点の違いも既存境界を維持する。ただし一般に不適切な資料選択を宣言した解法を、この探索器だけで意味的に修正する保証はない。

## 5. 純粋性・停止・予算

登録時に`純粋作用確認=True`を明示し、外部読取登録は拒否する。登録側は処理能力・検証能力に外部または永続的な副作用がないことを確認する責任を持つ。状態を持つModuleを使う場合も、呼出結果が隠れた副作用へ依存するものは対象外。

これは悪意あるPythonコードを隔離するサンドボックスではない。ファイル書込み・外部送信の巻き戻しはない。現実の状態を変更するツールの試行や外部取得を、この経路へ無言で追加してはならない。

既定は256解法展開、512能力呼出、分解深さ32。呼出数は処理・検証を含む既存合成器への呼出回数。能力本体が非該当・契約不成立で発火しなかった場合も呼出予算を消費する。上限で目的や検証条件を削らず保留する。入力と枝状態はそれぞれ1000000バイト、探索履歴8192件まで。厳密なメモリ・実行時間隔離は提供しない。

停止コールバックは展開・下位目的・能力呼出の前後で検査する。既存合成器内部にも渡す。登録コード内部の処理を強制中断する機能はない。停止判定器の故障、登録能力の名前・版変更、合成記録の整合違反は全体を止める。

## 6. 記録と限界

開始ハッシュに目的・解法・初期Data・能力版・予算を固定する。各記録は前ハッシュへ連結し、展開、呼出、目的検証、不成立、局所成立、後続からの再開、採用を追跡する。呼出の詳しい実行記録は合成器のハッシュで識別する。

`多段結果.整合確認`は記録と最終成果の内部整合のみを検査する。全コードを再実行する検査、署名、認証、独立した意味判定ではない。元データ・記録をまとめて変更し全ハッシュを再生成する攻撃の検出は保証しない。

`多段解決Module`は構造化された多段問題を既存Capabilityから呼ぶAdapter。各最終目的の構造化出力・経路・探索履歴を返す。標準チャットの入口へ自動接続する変更ではない。外側の合成器から内側への停止コールバックの自動伝播は既存能力契約にないため、直接実行APIと違い、外側ではModule呼出前後の停止となる。

## 7. 検証例

```text
最終目的: 原文の数値列をすべて抽出
下位目的: 抽出に使う素材を用意
候補解法: 1行要約を使う / 原文を保持する

原文: 売上は120です。費用は75です。利益は45です。
要約経由 → 120 → 元資料との数値列保持検査で不成立
子の別解へ戻る → 原文保持 → 120、75、45 → 検証合格
```

代替解法を外すと保留。原文の数値を731へ変えると731を含む列に追従する。原文自体が一文なら要約経由で保持検査を通るため、不要な代替を実行しない。

別の実装接続例では「Aの数値証拠」「Bの数値証拠」「同一尺度への関係化」「比較確定」を下位目的として解く。A≧120、B≦100なら比較確定。B≦200や適用条件不一致では未完了。前提を追加したり別の期待値へ変更したりしない。

```bash
python tools/多段解決デモ.py
python tools/多段解決デモ.py --代替なし
python tools/多段解決デモ.py --値 731
python -m unittest discover -s tests -p 'test_多段解決*.py' -v
```

## 8. 変更範囲と残作業

Core、HDS Compiler、既存の合成・証拠・関係・応答・取得Module、会話状態、GPQA正本、標準チャット、GUI-Shellは変更しない。

⑧全体の完成ではない。自由文からの目的・解法抽出、未知解法の生成、反例からの方法獲得、解法の意味的適合性の自動監査、外部作用を含む計画修復、最適計画、長期実行は未実装。有限の宣言済み解法について、子の実行結果を後続へ使い、失敗から経路を変更できる段階である。
