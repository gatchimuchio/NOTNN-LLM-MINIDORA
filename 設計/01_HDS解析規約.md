# HDS解析規約

## 0. 正本・運用拘束境界

この文書はMINIDORA/K3領域へのDomain Adapterであり、HDSを再定義しない。

LLM/Codexの運用拘束は、ルート[`AGENTS.md`](../AGENTS.md)の「HDS 大規模言語モデル運用拘束規約 v2.0」に従う。

優先順位:

```text
HDS正本
> AGENTS.md 運用拘束
> 本Domain Adapter
> 個別Run文書
> 実装都合
```

本Domain Adapterを、既存の英語圏方法論・第一原理思考・根本原因分析・仮説検証法・チェックリストへ翻訳して運用してはならない。

## 1. 目的

K3を構成部品へ分解することではなく、K3の観測結果から、LLM成立に必要な原理・責任・能力構造を抽出する。

## 2. 必須遷移

解析は最低限、次のHDS遷移を実際に成立させる。

```text
認知世界の暫定形成
→ 原理質問
→ 開放並列場
→ 原理の分別
→ 局所適用
→ 結果帰還
→ 総再開放
```

必要に応じて、正本のOpenParallelField、反対Model、不可能性、反実仮想、摂動、Whole-Field Return、Temporal Reconstitution等をこの遷移内で保持する。

前段が未成立なら、次段へ進んだことにしない。

## 3. 観測対象

K3について収集する対象は以下。

- 公開technical report
- 公開repository / config / code
- model card
- benchmark結果
- 入出力挙動
- reasoning effort差
- context長差
- Kimi Linear等の近縁系との差
- DeepSeek / Qwen / Llama / MiniMax等の異系統実装との差
- 公開ablation
- 計算量・遅延・memory・routing等の観測可能量

観測できないものは未観測として残し、一般論で補完しない。

## 4. 原理質問

最低限、以下を問う。

1. K3の言語能力を成立させている最小作用は何か。
2. その作用はK3固有architectureがなくても成立するか。
3. capabilityとknowledgeを分離すると何が残るか。
4. 長い直列処理のうち、必要責任と効率化実装をどう分けるか。
5. 状態・関係・条件・変換・継続/終了の最小集合は何か。
6. どの責任がLayer-0へ残り、どの構造が実装固有として消えるか。
7. architecture / training data / objective / post-training / RL / environmentのどこが観測能力を成立させているか。

原理質問は、表面問題の解答ではなく**何がこれを成立させているのか**へ接続する。

## 5. 開放並列場

一つの説明へ早期収束しない。

原理へ影響し得る、

- 別の対象化
- 別の関係
- 別Model / Mechanism
- 反対Model
- 不可能性
- 未観測
- 未説明残差

を、棄却根拠が成立するまで保持する。

例:

```text
Model A: KDA自体が能力源
Model B: KDAは状態保持効率化の実装

Model C: MoE自体が能力源
Model D: MoEは条件付き変換の実装

Model E: 巨大weight自体が能力
Model F: weightはCapability/Knowledge/Relation/Transformationの混成媒体
```

各Modelは、支持証拠、反証証拠、未解残差、予測を持つ。

## 6. 原理の分別

観測、共通点、相関、パターン、モデル、機構、原理を混同しない。

原理候補は少なくとも次へ答える。

```text
何が
どの関係によって
どの条件で
何を成立・変化させるか
何を変えれば崩れるか
どこまで適用できるか
```

十分に分別できないものは、機構候補・パターン・未解として保持する。

KDA / MoE / Attention / Transformer等の技術名そのものを原理へ昇格させない。

## 7. 反対Model・摂動・反実仮想

主要Modelには可能な限り反対Modelを置く。

例:

- 「KDAが必要」↔「KDAは不要、状態作用の一実装」
- 「MoEが必要」↔「Denseでも同責任が成立」
- 「内部Knowledge不可分」↔「外部Knowledge分離可能」
- 「architecture主因」↔「data/training/runtimeとの複合生成」

以下を用いて、実装固有物と成立構造を分別する。

- component除去
- budget縮小/拡張
- context長変更
- routing制約
- state保持制約
- 異architecture比較
- 同一taskでの別モデル比較
- 外部Knowledge固定/変更

実行できないprobeは未実行として保持する。

## 8. 水平引き算

複数実装を横に並べ、実装名を除去しても残る作用だけをLayer-0候補へ持ち込む。

Layer-0段階で、KDA / MoE / Attention / Transformer等の固有語が必要条件として残っている場合は解析未完了とする。

ただし「複数モデルに共通する」だけで原理とはしない。成立構造・崩壊条件・適用境界まで分別する。

## 9. 局所適用

原理候補を絶対化せず、現在の、

- 対象
- 条件
- 時点
- 目的
- 価値
- リスク
- 適用範囲

へ接続して、Layer-0責任・命令形P・評価設計等へ局所射影する。

MINIDORA側の既存設計仮説を、K3から発見した原理へ逆投影してはならない。

## 10. 結果帰還・総再開放

実装・評価・比較結果は結論だけへ返さず、必要に応じて、

- 原理
- Model / Mechanism
- 主体
- 対象
- 関係
- 因果
- 目的
- 評価規則
- 前提
- HDSによる対象化自体

まで戻して再監査する。

旧Projectionを削除せず、再解釈可能な形で保持する。

## 11. 実装禁止関門

次を満たすまで新しい能力実装を進めない。

- 原理質問が明記されている
- 最初の解釈以外を検査可能な状態で保持している
- パターンと成立構造を分別している
- 現在条件への局所適用がある
- 結果帰還/総再開放経路がある
- Layer-0へ持ち込む責任がK3固有機構名から分離されている

満たせない場合は`HDS適合不能`または`保留`とし、通常分析をHDS解析と呼ばない。

## 12. 出力と内部監査

HDSは出力書式ではない。利用者向け出力は依頼に最適化してよい。

ただし解析完了宣言前に、必ず次を監査する。

```text
私はHDSを実行したのか、それともHDSらしい言葉を付けただけか。
何がこれを成立させているのかまで到達したか。
最初の認知世界を固定したまま処理していないか。
結果によって再開放すべきものを残していないか。
```

一つでも成立しなければ、HDS解析完了を宣言しない。
