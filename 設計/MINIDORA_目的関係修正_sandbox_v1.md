## 1. 取得と検証の根拠

GitHubの固定コミットから取得したソースを、Git blob SHA-1で1ファイルずつ照合した。対象は `source_manifest.json` の全項目。本文をコピーしただけで同一性を推定せず、`blob <byte length>\0<bytes>` のハッシュ一致を確認した。

`base/` は一致を確認した元版、`snapshot/` はそのうち修正対象だけを置き換えた版である。実行に必要な31ソースファイルを復元して、**実物の `HDS実行主体.実行()` と通常循環、状態更新、認識・仮説・記憶・依存処理を実行**した。駆動核や状態更新をダミーに置き換えていない。

一方、全リポジトリのアーカイブとLibrary保存ZIPの実体は取得できなかった。各パッケージの元の `__init__.py` を含む全初期化経路は復元しておらず、再現環境では名前空間パッケージとして当該モジュールを読み込む。**通常のKernel初期化、全自然言語入口、全選択問題入口を通した統合成功を主張しない。**

## 2. 設計の変更点

### 原目的と、目的を成立させる経路を分ける

原要求・要求状態・要求認識・`HDS目的正本` は従来の目的契約署名で保護する。一方、目的依存経路は固定の許可表ではなく、作用の入力・生成物・消費先・継続依存から再構成する。

今回の議論との対応は次の通りである。

- 必要性: 原目的に接続された候補経路から、中間結果が必要になる関係を取得する。
- 到達状態: 原契約の要求状態・要求認識を保持し、途中成果を達成そのものにしない。
- 評価規則: 入力の成立、根拠・依存の有効性、実際の出力、最終検証によって採否を決める。

これは実装上の有限な射影である。**三項の数をハードコードした概念分解器、目的の普遍的な定義、任意の自然文を目的契約へ変換する能力を実装したという意味ではない。**

### 生産・消費・継続の共通契約

既存の `HDS作用仕様` に、後方互換の末尾フィールドとして `読取成果`、`生成成果`、`読取ノード`、`生成ノード`、`目的依存`、`契約完全`、`探索` を追加した。

型付きノードでは、状態・残差・認識・成果・仮説・枝・草案・形成・資料・主体・認識座標・観測要求を区別する。特に、**認識座標の登録、仮説の存在、認識の確定を同じ成立扱いにしない。**

`目的経路を構成()` は、生成側と消費側を固定点まで逆算する。途中で見つかった中間ノードについても明示的な目的依存を再照合する。`HDS目的経路` は根、候補経路上の必要ノード、生成・消費・前処理の接続、未構成作用、契約内で無関係な作用を保持する。

複数候補経路がある場合の必要ノードは候補経路の和集合であり、すべてが世界において絶対に必要という証明ではない。契約にない接続を、存在しないと断定しない。

### 実行・進展の分離

計画は成果や型付き中間結果の受渡しを扱う。ただし生成宣言は予定にすぎず、後続作用は実際の値と依存の有効性が成立するまで実行しない。計画側だけに書かれた入力条件も、実行側へ持ち込む。

進展は作用前に取得した必要関係について実際に新たな成立があったかで判定する。必要な成果の生成は、最終未達数が減らなくても進展になる。状態カウンターや目的ラベルだけの変化では延長しない。同じ成立の往復は進展台帳で二重計上しない。

### 未構成経路の有限な探索

`HDS探索契約` は、安定した契約ID、不明点、取得したい型付きノード、利用先、最大試行、最大資源を必須にする。既存の純粋作用を同じ通常循環から実行し、第二のエンジンは置かない。

取得予定を確定的な計画効果にはしない。空振りには目的進展を与えず、探索用の許可枠を別に消費する。現在の目的経路に利用先がなく、または上限を超えた探索は実行しない。履歴に契約署名と消費を残し、再開や作用IDの変更でも同じ契約の上限を復活させない。同じIDの契約・上限を無言変更すると拒否する。権限・明示停止・全体予算も維持する。

確認した正例は、明示された有限の対応取得から、信頼された既存作用の供給器が計算作用を構成し、回答へ接続するもの。任意の専門領域の法則を自動発見したり、資料中のコードを実行したりするものではない。

## 3. 個別の修正と受入

| 監査論点 | 修正 | 実測 |
|---|---|---|
| 座標登録後に仮説反映が止まる | 新規差分ではなく仮説の予測・参照対象から目的接続を保持 | 元版で失敗、修正版で仮説2件を保持。確定事実にはしない |
| 中間状態の明示依存を再照合しない | 固定点で明示依存と生産消費を再照合 | 同じ既存API入力で3工程が成立 |
| 生成側が目的経路に入らない | 成果の生産者と消費者を契約から接続 | ラベルなしの数量取得→計算→回答が成立 |
| 中間成果だけでは軟予算が続かない | 実際に成立した必要中間ノードを進展認定 | 初期予算1、3工程、延長2回で回答 |
| 目的ラベル付き内部更新が反復する | 進展と必要入力の変化を照合 | 元版8回、修正版1回。明示有限探索は別枠 |
| 成立済み内容が任意供給器の故障で失敗する | 目的成立・必要最終検証を供給より先に確認 | 供給器を呼ばず採用。最終検証失敗は採用しない |
| 未取得成果を機会判定・署名で読んで例外になる | 未成立入力では契約上の候補だけを取得 | 入力署名・意味署名・機会判定の3経路で不正な読取を回避 |
| 同一状態で仮説生成器を二重実行する | 作用インスタンスの単一状態キャッシュ | 同一状態では再利用し、状態更新後は再生成 |
| 無関係な作用の機会生成まで走る | 完全な操作契約の場合だけ構成前に除外 | 無関係作用の機会呼出0回。未記述は未構成として保持 |
| 予定成果が実現しなくても後続が動く危険 | 実値と依存有効性を実行時に確認 | 空の生産者の後に消費者を実行しない |
| 仮説と確定事実の混同 | 型付き入力の一致を要求 | 仮説消費は可能、同名の事実要求へは短絡しない |
| 学習済み手順が成果だけの工程を落とす | 手順再利用にも型付き入出力を照合 | 成果生成→消費の工程を維持 |
| 調査が無限反復する・再開で上限が戻る | 目的・探索契約ごとの消費を履歴から継承 | 試行数・資源・再開・動的作用ID・契約改変の反例を検証 |

供給、機会検討、計画、作用実行、射影について件数とナノ秒計測を追加した。機会検討自体にも有限の回数上限がある。ただし、**1回の外部コールバックを時間で強制中断する仕組みではない。**

## 5. 監査v3全体に対する残件

**ここを今回の54件成功で閉じてはいけない。**

| 残件 | 現在の境界 |
|---|---|
| 一般自然文・選択問題から新しい関係演算への通常入口統合 | 入力系・Kernel全体の変更と受入は未実施。明示型付き要求しか使えない制限を全面解消したとは言わない |
| 既存71件の型付き関係駆動試験 | 当該全依存と試験を復元しておらず未実行。既存関係核は書き換えていない |
| 任意の目的依存経路の自動発見 | 有限の契約・作用供給・明示探索を使う基盤まで。一般問題の方法構成能力は別の受入が必要 |
| 閉包後の記憶圧縮・経験形成を返却後へ分離 | 従来の同期後処理は残る。今回直したのは成立前の任意供給器故障との切り分け。返却待ち時間の解消を主張しない |
| 送達再試行と内容再推論の完全分離 | 出力・送達層を変更していない |
| 長寿命Coreの記憶寿命・全複製コスト | 仮説生成の二重実行は除去したが、全記憶複製・毎工程再評価の全面最適化は未実施 |
| 既存全3486試験と既知CI失敗 | 全件未実行。3件の既知失敗が消えたという結果はない |
| GPQA 198問 | 未実行。LIVE_ONLY・同一Core・一問一Kernel・事後採点を変更していない。正答率・速度改善は未測定 |
| Windows実機 | 未実行 |

監査v3で引用されたGPQA部分実行やCI集計を、本修正版の実測へ流用していない。今回確認したのは、**指定した構造上の切断の解消と、その正反対の受入条件**である。

## 6. 使い方

### このZIPだけで検証する

Python 3.13.5で検証済み。サードパーティー依存はない。

```console
python validate.py
```

実行履歴の合成例は `python examples/目的関係の実行.py`、適用器の8試験は `python test_packaging.py` で確認できる。

ログは `validation_output/` に出る。元版の意図した7失敗も再現するため、その標準出力に `FAILED` が含まれること自体は異常ではない。最終判定は `validation_output/summary.json` とプロセス終了コードを参照する。

### 固定基点の作業コピーに適用する

```console
python apply_patch.py /path/to/NOTNN-LLM-MINIDORA
python apply_patch.py /path/to/NOTNN-LLM-MINIDORA --apply
```

最初のコマンドは検査のみ。取得した元ソース全項目と変更対象をハッシュ照合し、矛盾する版・ローカル改変・不正なパスがあれば書き込まない。`--apply` は全対象の検査後に書き込み、変更前のファイルを対象ルートの `.minidora_patch_backups/` へ保存する。通信、git push、設定変更は行わない。

変更済みの同じ内容への再適用は何もしない。適用中の通常例外にはロールバックするが、電源断を含む複数ファイルの完全なトランザクションを保証するものではない。別の編集処理を同時に動かさない。

追加試験は `tests/目的関係修正_v1/` へ置かれる。リポの既存試験は変更しない。

```console
python -m unittest discover -s tests/目的関係修正_v1 -v
```

通常リポでは、そのプロジェクトの既存手順で `src` をPythonの検索対象にした環境から実行する。全面採用の判断には、上記残件の統合試験が必要である。
