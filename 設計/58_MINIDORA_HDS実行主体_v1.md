# MINIDORA HDS-first 実行主体 v1

日付: 2026-09-17  
状態: active internal core  
外向きLLM成立契約: `02_大規模言語模型成立契約.md` を維持  
模型核性能正本: `MINIDORA30` を置換しない

## 1. 目的

MINIDORA内部の制御主語を、通常MINIDORAからHDSへ移す。

外部説明では、MINIDORAは既存LLMの成立条件・能力作用を構文化し、非ニューラル方式で再実装するLLMである。この説明は変更しない。

内部開発では、MINIDORAの各実装を **HDSをLLMとして成立・駆動させる部品** として整理する。

```text
外部定義
MINIDORA = 非ニューラルLLM

内部実装原理
HDS = 目的・状態・残差・採否・再作用を所有する主体
MINIDORA部品 = HDSが起動する作用器
厳密言語模型核 = LLM成立条件を満たす独立模型層
```

## 2. 主体責任

HDS-first coreでは、次の責任をHDS実行主体へ一本化する。

- 目的の保持
- 現在の成立状態
- 未解残差
- 成果
- 主体状態の局所差分
- 利用可能作用の観測
- 次作用の選択
- 同一作用・同一入力の反復禁止
- 状態差の記録
- 再作用
- COMMIT / SUSPEND / FAIL

個々の能力モジュール、模型核、参照取得器、計算実行器、構文化器は最終COMMITを行わない。

```text
HDS実行状態
  ↓
HDS作用機会
  ↓
HDS作用選択
  ↓
既存部品を実行
  ↓
HDS作用結果
  ↓
HDS状態差
  ↓
HDS実行状態更新
  ↓
次作用 / COMMIT / SUSPEND / FAIL
```

## 3. 外向きLLM成立との分離

厳密言語模型核は引き続き、完全言語状態空間・持続模型状態・整合した言語確率法則を担う。

HDSの候補評価、作用状態、残差、能力得点を厳密言語模型確率へ変換しない。

```text
LLM模型成立
!=
HDS実行主体
!=
能力総量
```

従って、HDS-first化は `MINIDORA厳密言語模型` の置換ではない。

## 4. HDS構文化器

HDS構文化器は、MINIDORAへ入力を渡す前処理ではなく、HDS自身の認知作業状態を形成する知覚作用として扱う。

```text
自然言語入力
↓
HDS構文化作用
↓
HDS-IR
↓
HDS実行状態の成果
```

構文化器自身は採否・回答生成を行わない。

`HDSIR.実行可能` は旧計算実行境界の閉包判定である。HDS-firstでは、意味構文化成功と計算実行可能性を同一視しない。計算閉包を必要とする作用だけが `実行阻害理由` を要求する。

## 5. 汎用状態差

旧能力状態差循環の成立原則を、候補得点専用からHDS実行状態全体へ拡張する。

HDS状態差は少なくとも次を保持する。

- 前状態署名
- 後状態署名
- 追加・削除された成立状態
- 解消・追加された残差
- 変更された成果
- 変更された主体状態

```text
作用を実行した
!=
状態が変化した
```

状態差がない実行は履歴へ残すが、版を進めない。同一作用・同一作用入力署名を再実行しない。状態が実際に変化し、新しい入力署名になった場合だけ同じ作用を再利用できる。

## 6. 能力レジストリ

能力レジストリはHDSの道具箱であり、HDS-firstでは最終選択主体ではない。

```text
能力レジストリ
→ 適用可能な全候補
→ HDS作用Adapter
→ HDS作用機会
→ HDSが次作用を選択
```

旧製品経路の `能力レジストリ.選択()` はABI互換として残す。新経路では `候補群()` / `HDS作用群()` を用いる。

能力の `判定()` 値は、作用候補の局所優先度情報として利用できるが、回答正答率・HDS最終判断・COMMITとは同一視しない。

## 7. 模型核の向き

既存 `HDSMINIDORA模型評価` は互換の局所閉包を形成するが、HDS-firstではその `APPROVE` をシステム最終COMMITとして扱わない。

```text
HDS
↓
MINIDORA能力模型評価作用
↓
模型結果 / 回答候補 / 局所APPROVE
↓
HDS成果へ帰還
↓
HDSが目的・残差を再評価
```

`HDS模型評価作用` がこの射影を担う。

## 8. 既存HDS監督との関係

`32_MINIDORA_HDS監督介入制御_v1.md` の経路は、MINIDORA30 / GPQA正本 / 既存製品互換のため保持する。

旧経路:

```text
通常MINIDORA
↓
正常閉包なら透過
↓ 未閉包時だけ
HDS監督
```

新内部正本:

```text
HDS実行主体
↓
常時、目的・状態・残差から作用を選択
↓
MINIDORA部品
↓
HDSへ帰還
```

旧監督を削除したり、MINIDORA30の過去実測値をHDS-first性能へ読み替えたりしない。

## 9. K3境界

新しい `HDS実行状態` / `HDS状態差` / `HDS実行主体` はK3型へ依存しない。

旧 `HDS作業状態.py` のK3連携はMINIDORA30互換・履歴経路として保持する。K3 / GLM / Llama / ChatGPT等は、HDSが必要とする作用構造を観測する対象であり、HDS Runtime内部正本の型ではない。

## 10. 主体主幹との関係

永続的な主体ID・立場・選好・約束等をLLM成立条件へ混入しない。

HDS実行状態は、現在の目的・判断に必要な主体状態差分を局所保持できる。ただし外部の `主体主幹` を無言で置換・永続化しない。

```text
HDS局所主体状態
!=
永続人格
!=
LLM模型成立条件
```

## 12. 受入条件

1. 能力・模型作用の局所成功だけではHDS COMMITにならない。
2. HDSの要求状態が満たされ、残差が空の場合だけCOMMITする。
3. 残差を直接解消する作用を、無関係な高優先度作用より先に選ぶ。
4. 同一作用・同一入力署名を反復しない。
5. 実状態差があれば同じ作用を新しい入力で再利用できる。
6. 主体状態差をHDS状態差へ記録できる。
7. 能力レジストリが全候補をHDSへ公開できる。
8. HDS構文化器の意味閉包と旧計算実行閉包を混同しない。
9. 新HDS実行状態がK3型に依存しない。
10. 旧MINIDORA30 / MINIDORA80 / GPQA正本値を無言で置換しない。
11. 既存 `能力レジストリ.選択()` の結果順序を維持する。
12. Linux / Windows × Python 3.11–3.14で既存全回帰を通す。

## 13. 次段

次の性能改善は、作用数を増やすこと自体ではなく、HDSが次を構成できる範囲を広げることを優先する。

- 情報不足から必要観測を生成
- 新しい仮説候補の生成
- 候補を分別する追加観測・質問の選択
- 登録済み作用にない解法の構成
- 未知失敗からの修復作用構成
- 複数領域を横断した目的完遂

これらは既存性能残件 G014 / G026 / G028 / G034 / G036 / G071 と対応する。
